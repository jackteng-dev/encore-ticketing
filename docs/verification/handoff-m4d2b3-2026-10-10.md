## 本次完成內容

**M4D2B3：持久 recovery 任務、租約領取、有限重試、自動排程、未使用預扣期限 recovery 與程序重啟補做完成。** 沒有顧客預扣 coordinator／controller／啟用旗標／未知 intent UI；現有網站仍走原 PG 購票。內部恢復排程預設 false，任務在關閉時仍持久建立。

V10 新增 stock_recovery_job 與 immutable stock_recovery_claim，不改已發布 V1–V9。stock_hold_intent INSERT 同 transaction 建 UNUSED 任務，stock_hold_decision INSERT 同正式 worker transaction 建 SETTLEMENT 任務；enqueue SQL failure 回滾原 intent 或 order／stock／audit／journal／purchase 結果，不留半筆任務，consumer 不 ACK 成功。MQ ACK 後工作仍在 PG，不要求 Redis 先成功。升級僅 backfill 未受理且未 ABORTED 的舊 intent，以及未 ack 的正式 decision；舊業務資料不改。

StockRecoveryStore 用 PG clock／FOR UPDATE SKIP LOCKED 每次領取一筆，新 token／attempt／lease 與 immutable claim history 同交易保存。任務固定六次預算；失敗或程序死亡均消耗一次，重啟不重設。過期租約可接手，第六次租約過期轉 REVIEW。未知 IO／PG failure 失敗後等待1、2、4、8、16秒；最後 REVIEW。corrupt／反向 terminal／正式證據或 generation 衝突直接 REVIEW，不逆轉／INCR／重seed。終態、身份、budget 與 claim history 有 SQL guard；DONE 要有 domain 證據。

StockRecoveryWorker 為內部 bean，TICKET_STOCK_RECOVERY_ENABLED=false 預設不掃；明確 true 後每輪有限 batch。每個 domain phase 在 owner／ticket／purchase 或 progress 鎖後核對原 lease token／attempt／PG deadline，Redis 操作後、記 ack／ABORTED 前再 fence。job receipt update 也核對有效 lease。沒有外層未提交 transaction 包住多個 phase；已提交 DIRTY／ABORTING 仍先於 Redis。過期租約不能撤回已送出的 Lua，原不可變決定與 frozen ledger 終態讓下一個 worker 安全重讀，不宣稱跨系統 exactly-once。

StockHoldService.recoverUnused 在與 acceptance 相同的 owner／ticket／progress locks 下重驗原命令、acceptance 與 PG clock。尚 live 不放棄；accepted 只將 UNUSED 任務記為 ACCEPTED，不碰 Redis／progress HELD。未受理且到期才先提交 ABORTING＋DIRTY，再凍結／核對／release。已持久 ABORTING 首次任務立即可領取，不等原 deadline；失敗後仍遵守 backoff。accepted PROCESSING 由原 PurchaseExpiry／worker 保存正式 EXPIRED／RELEASE，再由 SETTLEMENT 核對，不能 raw abandon。

新增只讀 operational report（due、已決定 UNUSED、過期 lease、oldest due age、未解決 REVIEW／未 ack／ABORTING），不是公開管理 endpoint／Prometheus dashboard。詳見 [STOCK_RECOVERY](STOCK_RECOVERY.md)。

## 已知問題

recovery flag 預設 false，關閉期間工作只排隊不完成；未 ack／ABORTING／REVIEW 會繼續阻擋新 epoch。accepted PROCESSING 逾時仍須啟用原 TICKET_EXPIRY_ENABLED=true（預設），recovery 不代替正式 purchase expiry。REVIEW 不因 Redis 回來而自動重開；人工 domain 核對成功後，job 的 REVIEW 歷史仍保留，operational report區分 unresolved與history。

一次 settlement／abandonment 凍結整 epoch，仍在 PG ticket lock 中做短 Redis IO（connect／command各500ms、domain TX10秒）。claim預設 lease30秒、每輪10筆，實際 poll／鎖等待／冷啟動可能增加 queue age。有限 retry 用盡需人工核對，沒有吞吐或固定恢復 SLA。單 Redis/AOF everysec、單 MQ quorum、staff session JVM記憶體，無 Cluster／HA／負載／真收款宣稱。

KEY_MISSING／ABSENT 是投影遺失證據，不代表找回原收據。accepted progress HELD 是歷史，不得直接當成 active／raw abandon。手動改 DB／Redis、未登記 writer 或直接原語濫用不在本恢復保證內。沒有精確 context/token/usage介面；本輪保存完整可驗證 milestone，不再擴張入口實作。
