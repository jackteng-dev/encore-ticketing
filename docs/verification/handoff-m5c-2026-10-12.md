**M5C 雙 nonweb Worker 競爭、重複投遞與兩個實際 SIGKILL 邊界驗收完成。** 正式 Java／frontend／Compose／schema 不改，沿用相同已驗證 production JAR 與 dist，沒有 production debug API 或故障開關。

- Compose `--scale worker=2`：兩個相同 JAR 的 nonroot／rootfs唯讀 Worker，無 HTTP／host port，broker 真正有兩個 consumers。
- 十二份不同顧客意圖爭五個單位：五筆 RESERVED、七筆 SOLD_OUT，held5／sold0；健康 outbox 每個 intent 一次 publication attempt。HTTP 是順序送出，不是十二個並行 client 的負載 benchmark。
- 原事件再送八份 persistent／mandatory／confirmed duplicates；兩 Worker 同時停在原 PG owner lock，consumer channels 保留 unACKed delivery，放鎖後原訂單／HOLD／庫存仍一份。
- 真 broker confirm 後，PG publication receipt 在 private fixture trigger 等待時 SIGKILL；先保存 `1|true|true` 原未到期 lease，發布不等待消費結果。receipt transaction rollback，另一 Worker 依原15秒 lease 重新 claim／publish 同一 immutable event，attempts2、業務效果一份。
- PG lock 找出真正處理原請求的 Worker；先核對原 event publication 已確認、零訂單及 PROCESSING，再 SIGKILL。另一活躍容器取得原 unACKed delivery，仍在原交易等待，放鎖後只保票一次，victim 手動回歸。兩次 intentional exit137／OOM=false，先暫時 restart=no 避免自動重啟掩蓋，回歸恢復 unless-stopped。
- 真 PG／RabbitMQ tests 強化 independent OutboxStore＋真 TransactionTemplate／同步起跑，以及兩個 independent PurchaseConsumer 在 business commit 後 ACK loss 的 redelivery。後者是同 JVM 的獨立物件／真 broker channels，不假稱容器 kill 命中 commit 與 ACK 之間。

## 已知問題

- 單PG／Redis／RabbitMQ、Compose scale／restart不是HA或Cluster；本輪不是HTTP負載測試，不提供QPS／SLA。Nginx仍是static upstream／passive failure，API回歸需明確reload。
- API readiness只檢查PG，Worker沒有獨立readiness endpoint；用兩個broker consumers與真處理核對。HTTP／Secure=false僅explicit private fixture，不能直接公開。
- queue統計可落後channel delivery；ACK邊界保存直接consumer channel unACKed計數＋兩個PG client lock wait，drain也核對channels。另一consumer可立即取走requeued delivery，ready中間狀態不是必須捕捉的邊界。
- consumer容器kill點為business commit之前；commit後ACK loss另由真integration case驗證，沒有production hooks。confirm不代表已保票；未知回覆保留原UUID/body。
- work/m5c-20261012及本repo既有Maven/cache保存private env／原body／logs／所有失敗與成功證據。只讀既有已安裝完整JDK21，不修改其他repo，不global prune／清其他專案資源；沒有真模型或付費服務。
